# Phase 14 — Tests on GitHub (continuous integration)

**Status:** 🔧 Built and rehearsed locally (2026-11-13); first run on GitHub pending the push · Files: `.github/workflows/tests.yml` (new), `requirements.lock` (new), `README.md`

**Outcome in one line:** every push runs the 286 tests on a clean Linux machine with exactly the package versions used locally, and the commit gets a green tick or a red cross.

## Goal

Second item of the production list. Until now the tests ran only when someone remembered to run them, on one Mac, in an environment that had grown over 13 phases. Three things that could have gone wrong unnoticed:

1. **A change breaks something** and nobody runs the tests. The day before, moving files into folders silently turned two tests into skips. The count only showed up because the full run was read line by line.
2. **"Works on my machine":** a package missing from `requirements.txt`, a path that exists only on this Mac, or a file that only exists in the git-ignored `data/`.
3. **The big steps ahead** (the API backend and Docker) need a check on every step that doesn't depend on remembering.

## Step 1 — What the tests need on a clean machine

**Rehearsal setup:**
- a fresh `git clone` (no `data/` documents, index, secrets, `access.toml` or parse cache)
- a fresh environment installed only from the lock
- an empty home folder (`env -i HOME=<empty>`), so no downloaded models

| Run | Result |
|---|---|
| Offline (`HF_HUB_OFFLINE=1`) | 279 passed, **4 failed**, 3 skipped |
| Online | **284 passed, 2 skipped**, in 65 s |

- **The 4 offline failures** need downloaded models: 3 Docling/OCR tests, and an index test that loads the embedding model.
- **The third offline skip** needs the tokenizer.
- **Downloads:** the online run fetched **507 MB** into the Hugging Face cache: the embedding model `BAAI/bge-base-en-v1.5`, `docling-layout-heron` and `docling-models`. RapidOCR's models (31 MB) come inside its package.
- **The 2 skips are expected** and stay skipped on GitHub. Those tests read the evaluation documents, which are git-ignored and partly private (the lease email, the leave policy, the handwritten form), so they don't belong on GitHub. They and the evals keep running locally.

## Step 2 — Pinned versions: `requirements.lock`

`requirements.txt` only has lower bounds, so a clean install picks whatever is newest that day. CI would then test different versions from the ones in use. An upstream release (Docling, transformers, Streamlit) could turn CI red for reasons unrelated to the code, or green on versions nobody runs.

**What's in the lock:**
- It's built from the working environment's exact versions: `uv pip freeze` used as constraints for `uv pip compile requirements.txt --universal`.
- That gives 183 pins, every one the same version as installed locally. The 4 extra pins are packages that only apply on other platforms (e.g. `pywin32`).
- `--universal` keeps platform markers, so the same file installs on macOS and Linux.

**PyTorch, CPU only.** On Linux, PyTorch from PyPI is the CUDA build and pulls several GB of NVIDIA libraries that a CPU-only test machine never uses. With `--torch-backend cpu`, the lock pins:
- `torch==2.14.1+cpu` / `torchvision==0.29.2+cpu` on Linux
- the normal wheels on macOS

No NVIDIA packages are in the file.

**OpenCV:** the pinned build is `opencv-python-headless`, so no system graphics libraries are needed on the server.

**The rehearsal environment** installed from the lock in 11 s (uv's local cache) and imported torch 2.14.1, Docling and Streamlit 1.66.1.

The lock's header says how to regenerate it after upgrading packages. `requirements.txt` stays the human-readable list.

## Step 3 — The workflow (`.github/workflows/tests.yml`)

| Part | Choice | Why |
|---|---|---|
| When | every push, every pull request, and a manual "Run workflow" button | The project pushes straight to `main`, so pushes must be covered |
| Machine | `ubuntu-24.04`, 30-minute limit | A pinned image, not `ubuntu-latest`, so the OS doesn't change underneath; the limit stops a hung download |
| Permissions | `contents: read` | The job only reads the code |
| Concurrency | a newer push to the same branch cancels the older run | No queue of stale runs |
| Python + uv | `astral-sh/setup-uv@v10.3.3`, uv `0.13.5` (as locally), Python 3.12, an activated venv | The project is built with uv. `setup-uv` has no floating `v10` tag, so the exact release is pinned. Its package cache is keyed on `requirements.lock`, which its default patterns (`*requirements*.txt`) would miss. |
| Install | `uv pip install -r requirements.lock --torch-backend cpu` | Exact versions, CPU PyTorch |
| Models | `actions/cache@v6` on `~/.cache/huggingface`, keyed on the lock and `citerag/config.py` (model names) | The 507 MB is downloaded once, not on every push. When the key changes, the old cache still restores and only what's new is downloaded. |
| Tests | `python -m pytest -q -rs` | `-rs` lists skips with their reasons in the log, so a new skip is visible |
| Secrets | none | The LLM backends and Google sign-in are faked in the tests |

Action versions were checked against GitHub on 2026-11-13:
- `actions/checkout` v7.0.1
- `astral-sh/setup-uv` v10.3.3
- `actions/cache` v6.1.0

All three run on Node 24. The repository is public, so Actions minutes are free.

**Not rehearsed locally:** Linux itself (Docker isn't installed here). The rehearsal covered a clean checkout, a fresh environment from the lock, an empty home and model downloads, on macOS. The first GitHub run is the Linux check.

## Limitations

- **The evals don't run in CI.** They need the documents in `data/`, and the answer evals need an LLM key and spend money. They stay manual and local. A later step could run the retrieval eval on public documents only.
- **Hugging Face downloads are anonymous.** If Hugging Face throttles them on a cache miss, a run can fail for reasons outside the code; re-running fixes it.
- **Nothing enforces the result yet.** GitHub's branch protection can make `main` refuse commits whose tests fail. That's a setting in the repository's GitHub page, for later; with one developer pushing directly, the tick or cross plus the failure email is the signal.
